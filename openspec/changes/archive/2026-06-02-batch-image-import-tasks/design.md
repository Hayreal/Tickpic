## Context

当前 `StickerGen` 和 `ProductProcessing` 在各自组件里直接使用 `FileReader` 读取第一张文件，并把 data URL 写入局部 state。上传交互只覆盖单张拖拽和单张文件选择，没有粘贴入口，也没有文件系统落盘。任务中心则只在 `App.tsx` 里通过 `onAddTask(feature)` 追加一条简化记录，既没有真实任务状态，也无法关联导入图和输出图。

这次改动是一个跨层变更：前端需要统一导入体验，Electron 层需要提供本地存储能力，任务模型需要从“字符串日志”升级为“批次任务记录”。如果继续把逻辑拆散在各页面组件内，后续维护成本会快速升高。

## Goals / Non-Goals

**Goals:**
- 所有图片上传区域都支持批量拖拽、批量文件选择和聚焦后粘贴图片导入。
- 单次导入最多 4 张，导入后页面立即展示当前批次的全部图片。
- 导入图片按批次写入项目目录下的本地文件夹，生成输出也有独立目录。
- 只有在点击“开始生成”后才创建任务，并记录批次 ID、状态、导入记录、出图记录。
- 个人中心展示真实任务数据和状态流转。

**Non-Goals:**
- 不实现跨页面素材历史回显，也不提供全局素材库浏览器。
- 不在本次改动中接入真实远程生成服务，仍允许沿用现有模拟生成逻辑。
- 不实现超过 4 张的队列合并、分页导入或后台批处理调度。

## Decisions

- 新增统一的批次导入数据模型，而不是让每个页面维持各自的单图 state。
  - 原因：上传入口虽然分布在多个页面和子功能里，但校验规则、批次 ID、粘贴触发和落盘行为是一致的。
  - 备选：各组件自行扩展为 `string[]`。放弃原因是会复制大量拖拽、粘贴、校验和错误处理代码。
- 通过 Electron preload 暴露受控 API，由 main 进程负责写入导入文件、输出文件和任务存储。
  - 原因：当前渲染进程未开启 Node 能力，且本地写文件必须通过安全边界执行。
  - 备选：在渲染进程仅保存 base64。放弃原因是不能满足“文件存放在项目目录本地文件夹”的要求。
- 本地目录按批次和任务分层组织。
  - 原因：批次是导入边界，任务是生成边界，两者生命周期不同。导入目录建议使用 `storage/imports/<page>/<feature>/<batchId>/`，输出目录使用 `storage/outputs/<page>/<feature>/<taskId>/`，任务数据可放在 `storage/tasks/tasks.json`。
- “开始生成”时才创建任务，而不是导入即建任务。
  - 原因：用户明确要求个人中心不记录单独导入事件，只记录真正进入生成流程的任务。
- 任务记录保留导入图和出图图的本地路径元数据，并由个人中心读取展示。
  - 原因：这既满足“任务导入记录/任务出图记录”，也为后续“管理效果”详情视图提供基础。

## Risks / Trade-offs

- [Electron 文件 API 增加] → 需要设计 preload 类型和 main 进程目录写入逻辑；通过收敛为少量受控接口降低暴露面。
- [当前组件 state 结构较散] → 批次导入接入后会改动多个上传区；通过抽离共享 hook 或工具函数减少重复替换成本。
- [任务模型从 mock 升级为持久化结构] → 个人中心和 `App.tsx` 的数据流会变复杂；通过把任务创建、更新和读取集中到单一存储服务缓解。
- [输出记录目前仍为模拟生成] → 需要在模拟完成时补写本地输出文件，才能让任务记录完整；通过在现有完成回调处统一封装“写输出并更新任务”流程解决。
